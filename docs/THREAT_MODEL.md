# Threat model

What Grain proves, what it doesn't, and how each attack is met. Where a
mitigation is partial, it says so.

## What Grain claims

- **"This image matches record N."** A copy's watermark points to a record, and
  its 64-bit perceptual fingerprint is within a threshold of the one recorded.
  Anyone can check the distance against `FingerprintIndex.verify()` on Monad.
- **"Record N was registered by this account, at this time, with this signed
  manifest."** The contract stores the manifest hash; the manifest is signed
  by the creator's key; block order fixes the time.
- **"The creator declared how it was made"** (photo, artwork, AI-generated
  with a named tool), and, for agents, **"generated by ERC-8004 agent #N"**,
  shown as verified only when the chain confirms the signer controls that agent.
- **"The original carried this C2PA credential"** (e.g. OpenAI's), as read and
  validated in the creator's browser at registration.

## What Grain does not claim

- **That the first registrant is the author.** Grain proves who registered
  first, not who made it. A thief who registers a stolen image before its
  author does is credited. The mitigation is behavioural -- *register before you
  post* -- plus evidence: a recorded C2PA credential, and the creator's own
  earlier posts, can contest a registration off chain. There is no on-chain
  dispute process yet.
- **That a declaration is true.** "Photograph" or "AI-generated with ChatGPT" is
  the creator's signed statement. Grain doesn't detect AI; detectors are
  unreliable. A false declaration stays on the record, tied to the account that
  made it.
- **C2PA certification.** Grain follows C2PA's model of soft bindings and a
  manifest repository; it is not a certified C2PA implementation.

## Attacks

| Attack | What happens | Mitigation | Status |
|---|---|---|---|
| Strip the credentials (screenshot, re-upload, compression) | Embedded C2PA is gone | Watermark **and** fingerprint, independently; either finds the record | Measured: 21 images × 11 transformations; [WhatsApp](SURVIVAL.md) 7/7 |
| Crush the image until the watermark dies | Watermark unreadable | Fingerprint still matches | Measured: JPEG q20 kills the mark, not the fingerprint |
| Crop heavily | Fingerprint changes | Watermark survives a 10% crop | **Limit:** a 25% crop defeats both. Stated in the README. |
| Copy someone's watermark onto a different picture | The mark points to a real record | Cross-check: the copy's fingerprint must match the record's; otherwise **TAMPERED**, credited to no one | Measured: forged sample 32 bits apart → TAMPERED |
| Perturb an image to collide with someone else's fingerprint | Could cause false attribution | Two signals must agree for RESOLVED; a fingerprint-only match within 8–16 bits is shown as UNCERTAIN, not credited | **Not yet measured adversarially**; false-match rate measured on 210 unrelated pairs only |
| Register a near-duplicate of someone's image | Two records for one picture | First registration wins in resolution; the later one appears as a candidate | Partial: no block on near-duplicate registration |
| Unwatermarked original posted instead of Grain's copy | On some low-texture images, the watermark shifts the fingerprint, so the unmarked original can miss its record | Publish the copy Grain returns (the UI says so) | **Found 11 Oct:** 28 bits on a C2PA test image, 0–2 on seven ChatGPT images. Fix planned: index the original's fingerprint too |
| Lie about provenance from the server | The site, API or MCP could return a wrong answer | Every answer carries the on-chain distance; the browser can call `verify()` itself | By design |
| Stale or wrong indexer | Envio could miss or misreport | Indexed answers are checked against the contracts; reads fall back to the chain | By design |
| Rewrite the activity log | Grain could edit who checked what | The log is sealed on chain (`ActivityAnchor`); anyone's browser re-checks it | Proves no edits after sealing, not that each check was real |
| Claim an agent you don't control | Credit work to someone else's ERC-8004 identity | Shown as verified only if the signer owns the agent or is its registered wallet; the MetaMask plugin refuses to register for an agent the wallet doesn't control | By design |
| Fabricate a C2PA credential summary at registration | A creator's browser could sign "signed by OpenAI" for an image that never was | The record stores the original file's SHA-256: anyone with the original can re-validate it with any C2PA tool | **Partial:** without the original file, the summary is the creator's signed claim. Server-side or on-chain re-validation is future work |
| Link a pen name to its creator | De-anonymise a pen name | Each pen name is a separate account; its commitment is `keccak256(HMAC(key, pen) ‖ identity)`, noise without the tag | By design |
| Reuse a pen-name proof | A proof link is a permanent statement | It proves only that one pen name, is dated, and is signed by the identity | Proofs can't be revoked: share deliberately |
| Read someone's private note | Notes are on chain | AES-256-GCM under a key derived from the creator's passkey; only that passkey can decrypt | By design |
| Lose the passkey | Identity unrecoverable | Passkeys sync through the platform (iCloud Keychain, Google Password Manager); Grain stores nothing | Device-key fallback has weaker guarantees, and the UI says so |
| Pay a licence to the wrong address | Money to the wrong person | `LicenseRegistry` pays the record's creator, in full, in the same call | Measured on chain |
| Steer an AI assistant through record text | A title or note shown to an assistant could carry instructions | MCP tools return record data as plain text in a fixed format, and the server's instructions tell the assistant to cite, not obey | **Partial:** titles are creator-written; assistants should treat them as data |
| Drain the faucet | Spam registrations | Grants capped per account, priced from gas; testnet only | Mainnet plan: capped gas sponsorship |

## Contract properties, tested

Beyond the unit tests, [`test/Properties.t.sol`](../packages/contracts/test/Properties.t.sol)
checks properties for any input: `verify()` is exactly the Hamming distance;
every record sits in all 8 band buckets; manifest hashes round-trip; only the
creator can withdraw a record; a licence forwards exactly the price, refunds the
excess and leaves nothing in the contract; underpayment is refused. Invariants
hold across 4,096 random registrations, supersedes, withdrawals and licences:
ids are sequential, the index stays consistent with the records, withdrawal and
supersede are one-way, and the licence contract never holds funds. Gas is
snapshotted and checked in CI.

One behaviour worth stating: `LicenseRegistry` will license a withdrawn record
(the creator is still paid). The website, API and plugin refuse to offer it.

## Trust boundaries

- **Trusted by design:** Monad (the contracts and their state), the creator's
  device during registration (watermarking, signing, C2PA reading happen there).
- **Not trusted:** Grain's servers, the Envio indexer, the MCP server and
  verify API -- each answer can be checked against the chain.
- **Out of scope:** platform compromise of passkey providers, and legal
  questions of authorship.
